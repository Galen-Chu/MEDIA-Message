## 1. 決策記錄(提案,待拍板)

- **IA-D1 版面殼層複製文管庫(建議採)**:側欄+主區+toast 三件套照文管庫結構複製(沿用「複製不 monorepo」慣例);側欄品牌「媒」字 logo+MEDIA-Message,左下識別塊「媒管庫/社群媒體媒體發佈工具」。**logo 漸層沿用文管庫同組色**(家族一致、不動 palette 就不必重跑對比稽核),以字(文/媒)區分產品——若要異色,改色後須重跑 `scripts/contrast-audit.mjs`。
- **IA-D2 四頁籤命名與順序(命名 2026-10-11 維護者定案;不為對齊而開空殼頁籤)**:

  命名比照文管庫「中文+英文後綴」,兩組成對:「編發器 Media ↔ 編發器 Text」、「媒庫 Library ↔ 文庫 Library」。發佈史=**時間軸**(發過什麼、何時發),媒庫=**可重複使用的素材**(下次發文拿來用的東西),兩頁職責不重疊。定排程/自媒體是否另拆,等 M2/M3 多平台後再議(§2 U5)。
- **IA-D3 平台連線先留在編發器(建議採)**:M1 只有 FB,連線放發佈面板最順手;M2 YouTube 上線、連線數 ≥2 時,再評估比照文管庫抽出「自媒體 Social」連線中樞頁籤。
- **IA-D4 家族串接採「明確契約鍵」,不互讀內部資料(建議採)**:兩產品同源、技術上可直接讀對方的 `text-message:v2`/`media-message:v1`,但**否決直接互讀**——那會把對方的內部 schema 變成自己的依賴,對方任一次遷移就連帶壞掉,違反「兩產品路線圖互不綁架」。改為另立小型、版本化、雙方文件都記載的契約鍵(`family:*:v1`),各自只寫自己產出的部分(§3.2)。
- **IA-D5 串接分級推進,先低成本後高價值(建議採)**:L0 互相連結 → L1 說明素材交接 → L2 家族排程總覽 → L3 Gemini 金鑰共用(綁媒體 AI 候選,待該案拍板)。每級獨立可驗收,任一級可停。
- **IA-D6 媒庫 Library 範圍(頁籤 2026-10-11 維護者定案;內容分區待拍板)**:維護者定調「串接+媒體資料儲存庫」,建議分三區:
  1. **家族區(串接)**:文管庫切換卡(L0)、「來自文管庫」交接收件匣(L1:文管庫送來的文案,一鍵帶入編發器說明)、家族排程摘要(L2)。
  2. **說明素材區**:說明範本與標籤組(存目前說明/套用至編發器/刪除),比照文管庫文庫「文案管理」的操作語彙;純本機、零依賴,U1 即可上線。
  3. **媒體資料區——受紅線約束,只存 metadata 不存檔案**:「媒體檔絕不落地」紅線涵蓋 localStorage 與 IndexedDB(瀏覽器端持久化同屬落地),所以媒庫**不保存媒體檔本體**;可存的是媒體 metadata(檔名、類型、尺寸、時長、已發佈貼文連結、常用搭配說明/標籤)。平台回傳的縮圖網址是帶到期戳的簽章 URL,不可當永久預覽。**若要真正的「媒體檔庫」**,唯一不碰本產品後端的路徑是存到使用者自己的 Google Drive(文管庫已有「雲端列 Drive」模組可複製)——但這等於**修訂紅線措辭**(「絕不落地」→「僅落使用者自有雲端」),須維護者另案拍板,本提案不預設採行。
- **IA-D7 家族切換入口兩層、與文管庫對稱(建議採,需文管庫配合)**:①**側欄左下識別塊**放常駐切換連結(兩產品同位置、同樣式:「文管庫 ↗ / 媒管庫 ↗」),任何頁籤都一鍵可達;②**媒庫 Library ↔ 文庫 Library** 放深層串接(交接收件、排程摘要)。兩層位置與文案須兩邊一致——由本庫提案、文管庫 session 確認後各自實作(複製,不共用套件)。

## 3. 技術要點

### 3.1 同源的三個後果(U 系列之外也成立,建議先知悉)

1. **可串接**:同源 → localStorage、`BroadcastChannel`、`storage` 事件都共用,零後端即可交接資料(U3/U4 的基礎)。
2. **配額共用(現況就存在的風險)**:localStorage 約 5MB 配額以「源」計,**媒管庫歷史(上限 200 筆,含說明全文)與文管庫 `text-message:v2` 吃同一份配額**;文管庫 2026-10-09 才處理過配額用盡問題(其 `STORAGE_COPY`)。**現行程式的實際後果(2026-10-11 讀碼)**:`history.ts` 的 `persist` 未攔截 `setItem` 例外 → 配額滿時 `addRecord` 拋錯 → `App.handlePublish` 的 catch 靜默吞掉——**貼文其實已發佈成功**,但畫面無成功提示、檔案與說明不清空,使用者很可能再按一次造成重複發佈。**✅ 2026-10-12 已修**(獨立於 U1):`persist` 攔截配額錯誤、發佈成功提示不依賴歷史寫入成功、另行提示「紀錄未保存」(比照文管庫 O2 修法);U1 再一併評估歷史說明落地截斷長度。
3. **信任邊界一體**:任一產品出現 XSS,另一產品的 localStorage(含文管庫的 Gemini BYOK key)同樣可被讀取——這是已存在的事實,串接不擴大它,但 L3 金鑰共用的 UI 文案須誠實說明。

### 3.2 契約鍵草案(U3/U4;落地前兩 repo 各自在文件記載同一份)

```ts
// family:handoff:v1 —— 一次性交接(寫入方產生、讀取方取用後即刪除)
{ v: 1, from: 'text-message' | 'media-message', kind: 'caption', text: string, createdAt: number }

// family:schedule-feed:<product>:v1 —— 唯讀排程摘要(只寫自己的,只讀對方的)
{ v: 1, product: 'media-message', updatedAt: number,
  items: Array<{ platform: string; when: number; snippet: string /* ≤60 字 */ }> }
```

- 紅線不變:契約內**只有文字與 metadata**,媒體檔絕不進入;token 絕不進入。
- 讀取端一律防禦式解析(版本不符/格式壞=當作不存在,功能隱藏而非報錯),與降級模式同精神。
- 跳頁帶意圖:交接時以 hash 深連結(`/MEDIA-Message/#handoff`)開啟本庫並切到編發器;本庫目前無路由,U1 的 `activeTab` 宜預留「由 hash 初始化」能力。
- 模組 storage 可注入(比照 `services/history.ts`),vitest 斷言完整寫入形狀與取用即刪。

### 3.3 U1 實作注意

- **媒體檔狀態必須留在 `App` 層**:切頁籤會卸載頁元件,`file`/`previewUrl`/`caption` 若下放到編發器頁內,切到 Dashboard 再切回就會遺失選好的檔案;`useFacebook()` 也維持在 `App` 層,影片上傳中切頁籤不得中斷進度。
- 預覽 URL 的 revoke 時機不變(替換/移除/卸載 App)。
- 不新增全域 store:媒管庫狀態量小,`App` 內 useState+props 即可;等 M2 多平台再評估是否比照文管庫 `useAppStore`。
- UI 字串集中 `constants.ts`(頁籤名、統計卡標籤、篩選 chips)。

### 3.4 測試與驗收

- 單元:Dashboard 統計計算、History 篩選與排程狀態判定抽成純函式(`utils/`),配 vitest。
- E2E smoke:示範/啟用兩種建置下側欄四頁籤可切換、編發器可見媒體附件區(延續模式分歧擇一斷言)。
- 跨產品串接只在正式站同源下成立(本機兩個 dev server 埠號不同=不同源),驗收以正式站手動驗證+契約模組單元測試為主。
- Fork/自訂網域:若兩產品不在同一源,契約鍵讀不到→串接功能自動隱藏,不影響單產品使用。
